# ジャギー検出の誤検出率

- 調査時期: M1a
- 関連: 設計書 6.4 / D32，実装計画書 R22，付録 C 要調査 #1
- 再現: `cargo test -p px-io --test jaggy_rate -- --nocapture`

## 問い

ラン長の谷検出が実データで誤検出しないか (手描きの意図的な凹凸を違反と判定しないか)．

## 途中で分かった設計上の落とし穴

設計書 6.4 は「例外は曲率符号が反転する点 $\mathrm{Turn}(chain)$ の 1 箇所のみ」と
規定する．これを**ラン長列の最小値**として実装すると，

```
runs = [3, 3, 1, 3]     谷は添字 2．内部の最小値も添字 2
```

となり，**単発のジャギーが毎回「反転点」として見逃される**．最も普通のジャギーが
まさにこの形なので，規則が丸ごと無効になる．

反転点はラン長列だけからは決まらない — 「凹凸が入れ替わったのか，単に凸凹して
いるのか」の区別が付かないためである．**G2 の曲率場から符号を読む**形に直した．
ラン $i$ の前後で曲率の符号が入れ替わっていれば反転点とみなす．

これは G1・G3 だけでは足りず G2 が要るということであり，**基盤を先に揃える方針
(判断 6) が正しかったことの実例**でもある．個別実装なら `smooth` の中で
この問題に気付かず出荷していた可能性が高い．

## 追記 (M3) — **測定そのものが壊れていた**

`px smooth` を作るために測り直したところ，**下の表のラン数は 5 倍近く過大**だった．
輪郭追跡が幅 1 画素の部分を持つ形で**止まらず，上限で打ち切られていた** (D82) ．
最小の例は横に並んだ 2 画素で，32x32 の絵 1 枚がチェーン 14 万本になっていた．

| | 直す前 | 直した後 |
| --- | --- | --- |
| Aseprite 素材 11 件のラン | 1327 | **279** |
| `groups2` のラン | 841 | **21** |
| 検出 | 1 件 (0.1%) | 1 件 (**0.4%**) |

**率が低く見えていたのは分母が膨らんでいたからである．** 検出の中身は変わらない．

## 追記 (M3) — CC0 の実物 61 枚で測り直した

`px-calib jaggy` を作った (`--apply` で `px smooth` を実際に掛けた結果も出る) ．

| | 値 |
| --- | --- |
| ラン | 24714 |
| 検出 | 147 件 (**0.59%**) |
| 1 件でも鳴った絵 | **36 / 61 枚** |
| 移動上限 1 に収まる | 123 件 |

谷の周りの形で分けると，**理想の単谷形の底 (直してはいけないもの) は 1 件だけ**
だった (単発のくぼみ 137 ・片側だけ坂 9 ・曲率で除外 1) ．

`px smooth` を掛けると **61 枚で 104 画素が動き，ジャギーは 146 → 35** になる．
面積の変化は動かした画素数以内 ・2 巡目で動く絵は 0 枚 ・**lint の blocking が
増えた絵は 0 枚**である．

## 結論と限界

**検出率は 0.1%．誤検出で使い物にならないという状態ではない．**

ただしこの数字は**弱い証拠**である．

- 素材が Aseprite のテストスプライトであり，**手描きのドット絵ではない**．
  四角・点・文字といった単純な図形が多く，「意図的な凹凸」がそもそも含まれない
- 正解ラベルが無いので，検出 1 件が真陽性か偽陽性かを判定していない
- 測っているのは頻度であって誤検出率そのものではない

**R22 は閉じていない．** `testdata/lint-cases/positive/` に CC0 の良質なドット絵を，
`negative/` に自作の失敗例を揃えて，検出率と誤検出率の 2 本立てで測り直す
(実装計画書 5 章)．それが M2・M3 の閾値決定の前提になる．
